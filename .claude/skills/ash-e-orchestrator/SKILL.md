# ASH-E 오케스트레이터

**실행 모드:** 혼합 — 계획은 단일 서브에이전트, 구현은 서브에이전트 병렬, 검증은 서브에이전트 순차. 단계 A와 B 사이에는 사용자 합격 판정 게이트가 있다.

## 모델 배정
| 단계 | 에이전트 | 모델 |
| --- | --- | --- |
| 1 계획 | ash-e-planner | opus |
| A·B 구현 | perception-dev, priority-dev | sonnet |
| A·B 검증 | ash-e-qa | sonnet |

사용자가 "계획은 opus, 나머지는 sonnet"으로 정했다. 각 에이전트 파일의 `model:`을 따른다.

## 전체 흐름
```
1 계획(opus) → 2 사용자 확인
  → [단계 A: Windows 웹캠 프로토타입] 3A 구현 → 4A 검증/정확도 평가 → 5 합격 게이트(사용자)
  → [단계 B: ROS2 이식] 3B 구현 → 4B 동등성 검증 → 6 보고
```
단계 B는 사용자가 "프로토타입 합격"을 명시한 뒤에만 시작한다. 정확도가 불확실한 상태에서 ROS 배선을 얹으면 문제의 원인이 인식인지 이식인지 가려낼 수 없기 때문이다.

## 0단계: 맥락 확인
- `_workspace/`가 없으면 1단계부터.
- 있으면 어디까지 진행됐는지 파일(`02a`, `03a`, `02b`, `03b`)로 판단해 해당 단계부터 이어간다. 부분 수정 요청이면 해당 에이전트만 재호출한다(예: "우선순위만 다시" → priority-dev → ash-e-qa).
- 요구사항이 새로 바뀌었으면 `_workspace/`를 `_workspace_{timestamp}/`로 옮기고 새로 시작한다.
- 설계서의 인터페이스(core 타입, 메시지)가 바뀌는 수정이면 1단계부터 다시 한다.

## 1단계: 계획 (opus)
`Agent(subagent_type: "ash-e-planner")`로 `_workspace/01_planner_spec.md`를 만든다. 전달할 내용: 사용자 원문 요구, 대상 하드웨어(RPi5, Ubuntu 24, ROS2 Jazzy, 뎁스카메라), 개발 순서(Windows 웹캠 프로토타입 → ROS 이식), 우선순위 요구(다수 대상 순위, 타깃 이탈 시 다음 대상 전환).

## 2단계: 계획 확인
설계서의 "미결 질문"(뎁스카메라 기종, 학습 데이터 보유 여부, 프로토타입 합격선 등)을 사용자에게 보여주고 답을 받는다. 건너뛰지 않는다. 인터페이스가 잘못된 채 구현하면 되돌리는 비용이 크다.

## 3A단계: 프로토타입 구현 (sonnet, 병렬)
프롬프트에 "단계 A"를 명시하고 `perception-dev`와 `priority-dev`를 한 메시지에서 동시에 호출한다. 둘은 설계서의 `ash_e_core` 타입 정의로만 연결된다. 두 에이전트 모두 `windows-prototype` 스킬의 구조(core / prototype 분리)를 따른다.

## 4A단계: 프로토타입 검증 (sonnet)
`ash-e-qa`를 "단계 A"로 호출해 pytest와 정확도 평가를 실행하고 `_workspace/03a_qa_report.md`를 받는다. 결함은 담당 구현 에이전트를 재호출해 고친 뒤 재검증한다. 수정 루프는 최대 2회, 남으면 사용자에게 보고한다.

## 5단계: 합격 게이트
사용자에게 다음을 보여주고 판단을 받는다: 클래스별 precision/recall, 혼동행렬, 오검출 사례, 우선순위 오버레이 데모 실행법. 사용자가 웹캠으로 직접 시험해 볼 수 있게 실행 명령을 안내한다.
- 합격: 단계 B로 진행.
- 불합격: 오검출 원인(모델, 데이터, 안정화 파라미터)별로 3A로 되돌아간다. 필요하면 설계서의 인식 방식을 planner와 재검토한다.

## 3B단계: ROS2 이식 (sonnet, 병렬)
프롬프트에 "단계 B"를 명시하고 두 구현 에이전트를 동시에 호출한다. 검증된 `ash_e_core`는 수정하지 않는 것이 원칙이다. core 수정이 꼭 필요하면 그 사유를 보고받아 단계 A 평가를 다시 돌릴지 판단한다.

## 4B단계: 이식 검증 (sonnet)
`ash-e-qa`를 "단계 B"로 호출한다. 같은 영상을 프로토타입과 rosbag 재생으로 각각 돌려 결과가 일치하는지 비교하고 `_workspace/03b_qa_report.md`를 받는다. Windows에서는 ROS를 실행할 수 없으므로 RPi5 실행이 필요한 항목은 "미실행"으로 표시하고 사용자가 RPi5에서 돌릴 명령을 안내한다.

## 6단계: 보고
구현된 것, 실행하지 못한 검증, 남은 미결 사항, 다음 단계(주행 접근·넛지 연동은 범위 밖)를 요약한다.

## 데이터 전달
파일 기반: `_workspace/{phase}_{agent}_{artifact}.md`, 코드는 `src/ash_e_core/`, `prototype/`, `src/ash_e_perception/`, `src/ash_e_priority/`.

## 오류 처리
- 에이전트 실패 시 1회 재시도, 재실패 시 해당 결과 없이 진행하고 최종 보고에 누락을 명시한다.
- 웹캠을 열 수 없거나 모델 가중치가 없는 등 환경 문제는 재시도하지 말고 사용자에게 알린다.
- 에이전트가 하지 않은 판단은 추측으로 채우지 않는다.

## 테스트 시나리오
- **정상**: "웹캠으로 흡연자 구분부터 시험하고 싶어" → 설계서 → 확인 → 단계 A 구현 → 평가 보고 → 사용자 합격 → 단계 B 이식 → 동등성 검증.
- **불합격 루프**: 펜을 담배로 오검출 → 오검출 사례와 함께 3A 재진입 → 데이터/임계값/안정화 조정 → 재평가.
- **부분 재실행**: "거리 가중치를 높여줘" → 인터페이스 변경 없음 → priority-dev만 수정 → QA 재검증.
- **오류**: 모델 가중치 없음 → perception-dev가 스텁으로 인터페이스를 유지하고 notes에 학습 안내, QA 보고서에 "실추론 미검증" 표시.
